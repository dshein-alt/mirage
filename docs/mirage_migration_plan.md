Mirage implementation plan

Mirage is the initial project release. Mirage updates use a maintenance gate that drains in-flight writes before cutover and records recovery state before changing the live installation.
1. Gallery fullscreen viewer
- Add a translucent fullscreen button at the top left of each card. Use a card wrapper with separate native buttons for fullscreen and metadata. Each button opens its own dialog.
- Load the original image in a modal with a dimmed backdrop. Display small images at their natural size and scale larger images down to fit the viewport while preserving aspect ratio.
- Support the close button, backdrop click, and Escape. Add English and Russian accessible labels and return focus to the triggering button, or to a sensible fallback if the card is gone.
- Skip polling updates when the results are unchanged. Defer refreshes that would replace cards while a dialog is open, and preserve focus by image ID and action when a refresh does replace them.
2. Generation sizes and gallery history
- Offer SD 512×512, HD 1024×1024, and FHD 1920×1080, with HD as the default. Keep each model’s existing fast, medium, and high step counts. Preserve user-edited quality and sampling settings during migration.
- Validate the three exact preset IDs and dimension pairs. Remove --width and --height from the generation CLI and reject dimension overrides on fresh API requests. Queued jobs and retries keep their original resolved dimensions and runtime snapshots.
- Back up the generation configuration before migration. Map the stock small and medium presets to SD and large and hd to HD. Map custom defaults by exact dimensions where possible. Fall back to HD with a visible warning when no supported size matches.
- For new FHD jobs, pass 1920×1080 to sd.cpp. Center-crop an aligned result, such as 1920×1088, before hashing, thumbnailing, writing the sidecar, or publishing. Reject a result smaller than requested. Record the final 1920×1080 dimensions in the PNG, gallery row, and sidecar.
- Backfill historical gallery dimensions from readable PNGs and mark them verified. Preserve original images, sidecars, and job snapshots. Keep resolution=<id> for existing API and CLI callers. Add width and height filters for the new UI, combined with other filters using AND. Include verified historical sizes in the UI’s filter options.
- Reuse settings selects a preset by actual PNG dimensions. A valid unsupported size selects HD with an explanation. A missing or unreadable original shows an error and leaves the form unchanged.
3. Mirage branding and runtime identity
- Rename first-party UI and translations, brand assets, documentation, Python package, CLI, environment variables, container names and images, and package archives to Mirage. Update build helpers, Compose, packaging, and the lockfile. Keep stable-diffusion.cpp, sd-cli, and sd-server under their existing names.
- Add the project logo from `assets/mirage_logo.png` near the top of `README.md` and use the same artwork in the web UI header. Derive a small favicon from that logo and reference it in `web/index.html`. Serve the header logo and favicon as local static assets included in the app build.
- Use Mirage runtime image and container-prefix settings while preserving customized settings and paths. Resolve installer options in this order: explicit arguments, MIRAGE_*, persisted state, defaults. Store browser theme and language preferences under Mirage keys.
- Record the sd.cpp Git commit, runtime build ID, and immutable runtime image identity in each release manifest and new job snapshot. Build IDs must account for the source used, including dirty and nested submodule changes, and the build inputs that affect the artifacts. Execution and retry use the recorded build and image. Activation, status, and rollback expose the same identity.
- For every job, use the recorded build to locate the binaries and the recorded runtime image by immutable ID. Report a missing compatible image explicitly. Keep artifacts and images referenced by jobs or retained releases available.
4. Installer operations and source selection
- Implement orchestration in Python 3 with the standard library. Keep the shell build helpers. Offer install as the default, plus update and remove, using dialog or whiptail with a numbered fallback. Preserve model selection, local model import, and the ability to install without downloading models.
- In a local checkout, build from the current working tree, including uncommitted changes. Leave Git state untouched. Report missing submodules with instructions. Reuse verified artifacts for matching clean builds and use a separate build ID for dirty source.
- For standalone installation, resolve the latest published release from the canonical repository, fetch its source with pinned recursive submodules, and keep it in a persistent versioned directory. Keep user data outside those source directories. Document curl … | python3, use /dev/tty for prompts, and provide explicit non-interactive options.
- Persist non-secret installation state outside the source tree. Include the absolute data path, engine, launcher path, source reference, container and image IDs, and active and previous runtime builds. Resolve ambiguity before touching the installation. Obtain credentials from the environment or a secure prompt. Keep them out of installer files, journals, and logs.
- Require confirmation or --yes for remove. Remove the recorded application stack and owned launcher while preserving user data. Refuse removal while jobs are queued or running.
5. Update, rollback, and recovery
1. Lock and stage. Acquire a per-installation lock before inspecting the recovery journal. Resolve any interrupted operation before starting a new one. Build candidate images under unique tags and stage the runtime release without changing live tags or activation links.
2. Close admission and drain. For Mirage, journal the maintenance intent first. Acquire database-backed maintenance and check queued and running jobs in one transaction. Refuse a busy update. Once maintenance is active, block new shared-state mutations and wait for admitted writes to finish before stopping the service. Cover configuration, uploads, gallery and model writes, queue operations, and runtime activation or repair. Keep installer controls restricted to the installer.
3. Preflight the idle installation. Require the database to have no queued or running jobs. After maintenance and drain, stop the original container and retain it with its original configuration for recovery. If service state is uncertain, end preflight before changing live state.
4. Verify before migrating. Start a verification-only candidate with separate configuration, no queue workers, and no writes to live configuration or SQLite. Check its deployment ID and container image, then verify the staged runtime using its exact build and image IDs. Stop the verifier, take consistent SQLite and configuration backups, and run journaled offline migrations.
5. Commit before reopening admission. Start the final candidate in maintenance mode and verify its identity and runtime using the migrated configuration, explicit access mode, and published port. Activate the verified runtime and persist the new installation state. Durably record the commit before reopening admission and allowing workers to claim jobs.
6. Recover by inspecting actual state. Write each action’s intent durably before it changes live state. On failure or interruption before commit, stop the candidate, restore migrated state and activation links as needed, and restore the original running or stopped state. Health-check a restored running service. After commit, finish bringing the candidate online without restoring the old database. Make repeated recovery runs idempotent.
6. Acceptance checks
- Run uv run --locked --dev pytest -q and ./scripts/test.sh. Cover preset migration, removed overrides, preserved job snapshots, legacy filters, branding, translations, and installer operation and source selection.
- Test publication with a simulated 1920×1088 runtime result. Verify the cropped PNG, gallery row, sidecar, and SHA-256 agree, including after interrupted publication recovery. Verify exact FHD output with the pinned runtime for Qwen, MOSS, and Z-Image.
- Browser-check natural sizing, viewport fit, keyboard controls, focus return, polling, and both languages on desktop and mobile.
- Verify that the logo renders in the README and in the web UI header in light and dark themes, and that the deployed app displays the logo-derived favicon in the browser tab.
- On Docker and Podman, exercise install, update, and remove without model downloads. Verify data survives. Cover an authenticated install with a custom data directory, refusal while busy, an in-flight write during maintenance, concurrent installer attempts, candidate verification failure, and interrupted recovery before and after commit.
The canonical release repository URL and release host are needed for the published bootstrap and live standalone test. The remaining work can proceed using the local checkout and a release fixture.
